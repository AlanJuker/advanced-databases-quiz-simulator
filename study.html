Module 1 · Concepts, architectures & database types

A DBMS is the software that stores, protects and shares data. Its key design idea is to keep what users see separate from how data is stored.

1.1 Database vs DBMS vs database system

TermWhat it isLibrary analogy
DatabaseA collection of related data that represents part of the real worldThe books
DBMSThe software that defines, stores, retrieves, updates, protects and shares the dataThe librarian and the catalogue system
Database systemDatabase + DBMS + the applications that use themThe whole library, working
  • Miniworld (universe of discourse): the part of the real world the database represents, e.g. students and courses.
  • Data is the content (names, grades). Metadata is data about the data (table names, data types, constraints). The DBMS keeps metadata in the database catalog.
  • A query asks for data. An update changes data. A transaction is several steps that succeed or fail together.

1.2 The four DBMS characteristics

CharacteristicMeaningExample
Self-describingIt stores its own structure in the catalogIt knows which columns STUDENT has
Program-data independenceApps don't depend on how data is physically storedStorage changes, the app keeps working
Multiple viewsEach user group sees its own partA student sees their transcript; the registrar sees all grades
Shared multiuserMany users at once, and the data stays correctHundreds of students registering at the same time

1.3 Who works with the database

  • DBA (database administrator): access, security, performance, backups.
  • Database designer: decides what data to store and how to structure it.
  • Application programmer: writes the software that sends requests to the DBMS.
  • End users: use apps, forms, dashboards and reports.

1.4 Data models, from human to machine

  1. Conceptual: entities, attributes and relationships (Student, Course). Close to how people think.
  2. Representational (implementation): the relational model, i.e. tables with rows and columns.
  3. Physical: how data sits on disk (record formats, indexes, file organization).

1.5 Schema vs instance

SchemaInstance (state)
WhatThe blueprint: structure, types, constraintsThe actual data at one moment
ChangesRarelyAll the time
ExampleSTUDENT(Student_ID, Name, Program_ID)The 1,000 student rows stored today

Admitting a new student changes the instance, not the schema. Data abstraction means users work with concepts like "my transcript" without seeing disk details.

1.6 The three-schema architecture

  • External: what each user group sees. It hides what they don't need.
  • Conceptual: the full structure for everyone, with no storage details.
  • Internal: how data is physically stored.
  • A mapping translates a request down the levels, and the results back up.
  • Goal: separate applications from physical storage.

1.7 Data independence

TypeYou can change……without changingExample
LogicalThe conceptual schemaUser views and appsAdd a Preferred_Name attribute
PhysicalThe internal schemaThe conceptual schemaAdd an index, reorganize a file

Memory trick: physical = disk, files, indexes. Logical = attributes and structure.

1.8 Languages and interfaces

  • DDL (Data Definition Language) defines structure: CREATE TABLE. DML (Data Manipulation Language) works on data: SELECT, INSERT, UPDATE, DELETE.
  • Procedural: you say how to get the data. Nonprocedural / declarative (like SQL): you say what you want.
  • Interfaces: menu-based, forms-based, query interface (typing SQL), application interface (apps through drivers or APIs).

1.9 Architectures and environments

ArchitectureIdea
CentralizedEverything at one site (old mainframes)
Two-tier (client/server)Client = user interface. Database server = DBMS.
Three-tierClient → middle layer with the application logic → database server
DistributedData spread across networked sites. Benefits: availability, scalability, local access. Challenges: consistency, coordination, security, recovery.
CloudCloud infrastructure: elastic scaling, managed backups, global access

DBMSs are classified by data model, number of users (single-user or multiuser), number of sites (centralized or distributed) and purpose (general or specialized).

1.10 Which database type fits?

If the data is…UseExample

Exam traps.
  • Database ≠ DBMS. The database is the data. The DBMS is the software.
  • Three-schema (levels of description) ≠ three-tier (layers of servers).
  • Adding an index = physical independence. Adding an attribute = logical independence.

Check yourself

A DBA adds an index and nobody's queries change. Which independence is this?

Physical data independence: the internal level changed, and the conceptual level did not.

What changes when a grade is updated: the schema or the instance?

The instance (state). The schema is the blueprint and stays the same.

Which characteristic lets the registrar and students see different things?

Multiple views.

Customer referral chains: which database type?

Graph, because the relationships are the main interest.

Module 2 · Storage, buffers & indexing

Disk is slow and memory is small. So the DBMS reads whole blocks, keeps useful ones in a memory buffer, and uses file organization and indexes to avoid reading data it doesn't need.

2.1 The storage hierarchy

LevelExamplesSpeedSurvives power loss?Used for
PrimaryMain memory (RAM), cacheFastestNo (volatile)Data being processed now
SecondaryHDD, SSDSlowerYes (nonvolatile)The database itself
TertiaryTape, opticalSlowestYesBackups and archives

Databases hold persistent data, which must survive restarts. They aren't kept only in memory because memory is too small, more expensive and volatile. Only the blocks that are needed are brought into memory.

2.2 Disks, blocks and access cost

  • A block (page) is the fixed-size unit moved between disk and memory. To read one record, the DBMS reads the whole block.
  • A track is a circle on the disk surface, and a sector is part of a track. A cylinder is the same track across all surfaces.
  • Disk access time = seek time (move the head to the track) + rotational delay (wait for the block to spin under the head) + transfer time (copy the data to memory).
  • SSDs have no moving parts, so they avoid mechanical delays. Good design (buffers, indexes) still matters.
  • A full scan reads every block. That's fine for small files and expensive for big ones.

2.3 The buffer pool

A buffer is a memory area that holds one block. The buffer pool is many buffers. The buffer manager decides which pages stay in memory and which get replaced. Reusing a page that's already in memory avoids a slow disk read.

FlagMeansRule
Pin-countHow many users or processes are using the page right nowIf it's above 0, the page is pinned and must not be removed
Dirty bitThe page was changed in memoryWrite it back to disk before removing it

Can this page be replaced? If it's pinned, no. If it's dirty, write it back first. If it's clean and unpinned, it can go immediately.

Double buffering uses two buffers, so the CPU works on one while the disk fills the other.

Replacement policyRemoves the page…
LRU (least recently used)Not used for the longest time
FIFO (first-in, first-out)That arrived first, even if it's still used a lot
ClockLike LRU but cheaper: recently used pages get a "second chance"

Example. Pages A, B and C are loaded in that order, then A and C are used, and D needs room. LRU removes B, the one not used for the longest time. FIFO removes A, the one that arrived first.

2.4 Records and files

  • A record is a group of related field values (Employee_ID, Name, Salary).
  • With fixed-length records, the DBMS can calculate where each record starts. Variable-length records suit optional or varying fields.
  • An unspanned record must fit inside one block. A spanned record can continue in the next block, which is needed when a record is bigger than a block.
  • The file header (descriptor) stores the record format, field sizes and block addresses.

2.5 File organizations

FileHow records are storedGood atBad at
Heap (unordered)In arrival order, appended at the endFast insertsSearching (needs a full scan)
SortedOrdered by a sort keyReading in orderInserts (the order must be kept)
HashedA hash function turns the key into a bucketExact matches (ID = 1005)Ranges (ID between 1000 and 2000)

2.6 Indexes

An index is an extra (auxiliary) structure, like the index at the back of a book. It stores search key values with pointers to the records. It doesn't replace the data file; it is another way to reach the records.

IndexBuilt onExample
PrimaryThe file's ordering field, which is uniqueFile sorted by Student_ID
ClusteringThe file's ordering field, which is not uniqueFile sorted by Department
SecondaryA field that is not the ordering fieldFile sorted by ID, index on Email

Trade-off: indexes take extra storage and slow down every insert, update and delete. Index the fields that are searched often, not every column.

2.7 Enterprise storage

  • RAID: striping spreads data across disks for speed. Mirroring keeps a duplicate copy for reliability. Parity stores extra information to rebuild a failed disk.
  • NAS provides file-level storage over a network. A SAN provides block-level storage over a specialized network.
  • Storage tiering keeps hot data on fast storage and cold data on cheap storage.
Exam traps.
  • LRU looks at the last use. FIFO looks at arrival time.
  • A dirty page can still be replaced, but only after it's written back. A pinned page can't be replaced.
  • Hashing is great for exact matches and bad for ranges.
  • Faster SSDs don't remove the need for indexes and buffering.

Check yourself

P1: pin 0, dirty. P2: pin 2, clean. P3: pin 0, clean. Which page can go without writing to disk?

P3. P1 must be written first, and P2 is pinned.

Which file organization makes inserts expensive?

Sorted, because every insert has to keep the order.

The file is ordered by Student_ID. What kind of index is an index on Email?

A secondary index, since Email is not the ordering field.

Why not index every column?

Every index costs storage and slows down inserts, updates and deletes.

Module 3 · Specialized & hierarchical data models

When data involves time, location, media content, rules or levels, a specialized model fits better than plain rows and columns. Choose by the data and the questions it must answer.

3.1 Match the requirement to the model

Clue in the questionModelExample
Parent–child levels, a treeHierarchicalOrg chart, folders, reporting lines
"Automatically when…", alertsActive (triggers)Automatic safety alerts, reorder stock
History, "on a past date", audit trailTemporalHistorical permits, salary history
Location, distance, inside, nearestSpatialRoad maps, delivery zones
Images, video, audio searched by contentMultimediaTraffic-camera video
Infer new facts from rulesDeductiveRegulations and inferred eligibility

One system can combine several models. The city platform from the in-class activity uses all six.

3.2 Hierarchical model

  • A tree where each child has exactly one parent: Faculty → Department → Program → Course.
  • Good for file systems, org charts and category trees. Navigation from parent to child is fast.
  • Limit: many-to-many relationships. A student takes many courses, and a course has many students.
  • In-class activity: a course that belongs to two programs needs two parents, which breaks the tree. Fix it with a relational Program–Course link table (or a graph), and keep the tree only as a navigation view.
  • XML and JSON still use hierarchical (nested) structure.

3.3 Active databases and triggers

An active database reacts automatically to events. Its tool is the trigger, a rule that fires on INSERT, UPDATE or DELETE. Rules follow the ECA model:

EventWhat starts it: an INSERT or UPDATE on Inventory
→
ConditionThe test: quantity < reorder level and no open request
→
ActionThe response: create one replenishment request
  • Why a trigger instead of app code? The rule runs on every change, whichever app made it.
  • Caution: triggers can chain (one fires another) and create loops. Design, document and test them.

3.4 Temporal databases

A temporal database keeps history instead of overwriting old values. A time point is one moment. A time period has a start and an end.

TimeMeaning
Valid timeWhen the fact is true in the real world
Transaction timeWhen the database recorded the fact
BitemporalBoth are stored

In-class activity: a salary of $82,000 is effective Jan 1 and entered on Jan 10. On Feb 3, HR corrects it to $84,000.

VersionSalaryValid fromRecorded on (transaction time)
1$82,000Jan 1Jan 10
2 (correction)$84,000Jan 1Feb 3

Tuple versioning keeps several versions of a row, each with its time period. The cost is more storage. If only the current value matters, you don't need a temporal model.

3.5 Spatial databases

A spatial database stores objects as points (a store), lines (a road) and polygons (a city boundary or flood zone). Location queries need spatial indexes, because normal indexes don't handle 2D or 3D coordinates well.

QueryFindsExample
RangeObjects inside an areaHospitals inside the flood zone
Nearest neighbourThe closest objectThe ambulance closest to an accident
Spatial joinMatches between two sets of objectsShelters that intersect evacuation districts

3.6 Multimedia databases

  • Images, video, audio and documents. Their meaning is in the content, and a filename says almost nothing about it.
  • Content-based retrieval finds items by analysing them (colour, shape, objects, sound patterns).
  • Semantic tagging adds labels such as "campus" or "snow", manually or automatically.
  • In the schema, store file references and metadata, and keep the big files in separate storage.

3.7 Deductive databases

A deductive database = stored facts + rules → it infers new facts that were never stored. It is useful for indirect or recursive relationships, such as everyone above you in a supervision chain. Datalog is its rule language. A rule has a head (the conclusion) and a body (the conditions).

graduate_student(maya).
enrolled(maya, advanced_databases).
lab_access(X) :- graduate_student(X), enrolled(X, advanced_databases).
→ derived fact: lab_access(maya).

3.8 Choosing a model

Pick the model that fits the data and the questions, not the most sophisticated one. Each model adds cost: temporal needs more storage, spatial needs spatial indexes, multimedia needs content analysis, and deductive needs well-designed rules.

Exam traps.
  • Valid time = the real world. Transaction time = the database. A correction keeps its valid time and gets a new transaction time.
  • "Inside an area" = range. "Closest" = nearest neighbour. "Two sets compared" = spatial join.
  • Hierarchical models fail with many-to-many relationships.

Check yourself

"Automatic safety alerts" in the city platform: which model?

Active database rules (triggers).

In ECA, which part decides whether the rule runs?

The condition.

Which shelters intersect the evacuation districts? Which query type?

A spatial join, because it compares two sets of objects.

What new fact comes from the Maya rule?

lab_access(maya).

Module 4 · Schema design, integrity & storage strategy

The schema is the blueprint. Keys identify each row, constraints keep values valid, and transactions move the database from one valid state to another.

4.1 Relational vocabulary

TermEveryday wordExample
RelationTableSTUDENT
TupleRowOne student
AttributeColumnEmail
DomainAllowed valuesGPA from 0.00 to 4.00, grades A–F
DegreeNumber of attributes5 columns → degree 5
Relation stateThe rows right nowToday's 1,000 students
  • Atomic means indivisible for the system's needs. If you search by city, split the address into Street, City and Postal_Code.
  • In the formal model, rows have no order and no duplicates are allowed.
  • A valid state satisfies all constraints.

4.2 The three meanings of NULL

MeaningExample
Unknown: the value exists but isn't recordedPhone number not provided yet
Not applicable: the attribute doesn't applyVisa_Status of a domestic student, manager_id of the CEO
Not yet assigned: it will be filled in laterAdvisor_ID before assignment, termination_date of an active employee

NULL doesn't say why a value is missing, so it is ambiguous. Add a status attribute if the reason matters.

4.3 Keys, step by step

  1. Superkey: any set of attributes that is unique. It may have extra attributes, like {Student_ID, Email}.
  2. Key: a minimal superkey, with nothing extra, like {Student_ID}.
  3. Candidate keys: all the minimal keys, e.g. Student_ID, Email and Government_ID.
  4. Primary key: the candidate key you choose. It must be unique, minimal, stable and never NULL. A system ID beats an email (emails change) and a name (names repeat).
  5. Unique key: the other candidate keys. They get UNIQUE + NOT NULL.

Composite key: ENROLMENT(Student_ID, Section_ID, Grade) needs both IDs, because the relationship is many-to-many. A foreign key is an attribute that references another table's primary key.

4.4 Types of constraints

TypeComes fromExamples
InherentThe data model itselfNo duplicate tuples
Schema-basedDeclared in the schemaDomain, key, NOT NULL, entity integrity, referential integrity
Semantic (business rules)Organizational policyAt most 5 courses per term. Enforced by app code, triggers or procedures.
  • Entity integrity: the primary key can never be NULL.
  • Referential integrity: a foreign key must match an existing primary key (or be NULL if allowed). This prevents orphan records.

4.6 Deleting a row that others reference

OptionWhat happensUse when
RestrictThe delete is rejectedDependents can't exist without the parent (active courses need a department)
CascadeThe dependent rows are deleted tooDependents are meaningless alone. Dangerous: it can erase lots of data.

In-class activity: for historical budgets, don't delete the department at all. Mark it inactive so the history stays intact.

4.7 Transactions

A transaction is all or nothing. A transfer subtracts $500 from account A and adds it to account B. If the system fails in between, the money would vanish. As one transaction (BEGIN … COMMIT), a failure causes a ROLLBACK and nothing changes. The database always moves from one valid state to another.

4.8 Turning requirements into design

NeedDesign choice
Hierarchy in a relational tableA self-referencing foreign key: EMPLOYEE(Employee_ID, Name, Supervisor_ID)
TemporalStart and end dates, timestamps, versioned rows
SpatialCoordinates, spatial data types, spatial indexes
MultimediaFile references and metadata, with the files stored separately
ActiveTriggers, alerts, rule procedures
DeductiveFact tables and rule structures

Logical design captures meaning. Physical design (indexes, storage) follows the access patterns. For example, a parcel service searches by tracking_number and by customer within a date range, so it needs a unique index on tracking_number and an index on (customer_id, delivery_date). Old deliveries can be partitioned by date.

Exam traps.
  • Degree = number of columns, not rows.
  • {Student_ID, Email} is a superkey but not a key, because it isn't minimal.
  • Entity integrity is about the primary key. Referential integrity is about foreign keys.
  • A wrong value or type is a domain violation. A missing referenced row is a referential violation.

Model answers for likely open questions

Two or three sentences each: a definition, then a contrast or an example.

Database vs DBMS vs database system

A database is a collection of related data that represents part of the real world. A DBMS is the software that defines, stores, retrieves, protects and shares that data. A database system is the database plus the DBMS plus the applications that use them.

The three levels of the three-schema architecture

The external level holds user views. The conceptual level describes the whole database (entities, relationships, constraints) without storage details. The internal level describes physical storage. Mappings connect the levels, so applications are separated from storage.

Logical vs physical data independence

Logical data independence means the conceptual schema can change, for example by adding an attribute, without changing user views or applications. Physical data independence means storage can change, for example by adding an index, without changing the conceptual schema.

What the buffer manager does and why buffering helps

The buffer manager keeps disk blocks in a memory buffer pool and decides which pages stay or get replaced, using the pin-count, the dirty bit and a policy such as LRU. Disk access is much slower than memory, so reusing pages already in memory avoids repeated disk reads.

What an index is and its trade-off

An index is an auxiliary structure that stores search-key values with pointers to records, so the DBMS can avoid full scans. It costs extra storage and slows down inserts, updates and deletes, so index only frequently searched fields.

Valid time vs transaction time

Valid time is when a fact is true in the real world, for example a salary effective Jan 1. Transaction time is when the database recorded it, for example Jan 10. A bitemporal database stores both.

The ECA model

Event: what triggers the rule, such as an insert or update. Condition: the test that decides whether to act, such as quantity below the reorder level. Action: what the system does, such as creating a replenishment request.

Why a strict hierarchy fails when a course belongs to two programs

A strict tree gives each child exactly one parent, but a shared course needs several parents, so the relationship is many-to-many. Store the entities relationally with a Program–Course link table (or a graph), and keep the tree only as a navigation view.

Entity vs referential integrity

Entity integrity says a primary key can never be NULL, so every row can be identified. Referential integrity says a foreign key must match an existing primary key, which prevents orphan records.

Superkey vs candidate key vs primary key

A superkey is any set of attributes that uniquely identifies rows, possibly with extras. A candidate key is a minimal superkey. The primary key is the candidate key you choose: unique, stable and never NULL.

Why run a money transfer as a transaction

The debit and the credit must both happen or neither. Inside a transaction, a failure triggers a rollback, so the database moves from one valid state to another and money never disappears halfway.

The three meanings of NULL

Unknown (a phone number not provided), not applicable (Visa_Status for a domestic student) and not yet assigned (Advisor_ID before assignment). NULL alone doesn't say which, so it is ambiguous.
